# Notebook-owned conversation lifecycle

Owner clarification: one conversation per notebook, initialized at creation and resumed at reopen; no New conversation/selector. Agent engine remains next phase.

**Recommendation: approve the direction, with a required lifecycle design constraint.** The canonical conversation must be server-owned and notebook-scoped, not a fake Default Project or a browser-stored ID. This is a minimal persistence extension, not the agent engine.

- **Durable seam:** Add a SQLite `canonical_notebook_conversations` mapping keyed uniquely by notebook ID, with a unique conversation ID. Implement one `ensure(notebook_id)` operation in `ApplicationStore`: verify the notebook file is present, then get-or-create the mapping and conversation in one `BEGIN IMMEDIATE` transaction. The existing notebook-lock → application-lock → SQLite order (`application/store.py:1–5,109–124`) and uniqueness make concurrent create/reopen return the same ID. Expose a notebook-scoped lookup/ensure route; call ensure after `POST /notebooks` creates the file and when opening a notebook. Do not put the mapping in mutable `.ipynb` metadata.
- **Standalone storage:** Current `records` CHECK requires `project_id` for every non-project record (`application/store.py:44–51`), while `ConversationCreate` requires a project (`models.py:36–43`). Use an additive, versioned migration that permits **only notebook-owned conversations and their messages** to have `project_id=NULL` and requires a notebook ID for that branch; retain existing project records and public project-scoped contracts. That is preferable to weakening the CHECK generally or adding a second message journal. New canonical conversations can be notebook-owned even when the notebook currently belongs to a project; membership changes then cannot change their identity.
- **Legacy policy:** Create a fresh canonical conversation for pre-existing notebooks lacking a mapping. This avoids guessing which of multiple legacy threads is “the” conversation or silently moving project-owned history. Keep all legacy rows and project-only threads accessible as historical, read-only notebook-scoped history where their recorded `notebook_id` exactly matches; leave project-only history in project context. Never render a project-wide thread as this notebook’s conversation. Document this explicit non-merge policy. Notebook-scoped `POST /conversations` must not create parallel threads; preserve project-only legacy creation where compatible and give old notebook-scoped callers a clear conflict or documented canonical-ensure response.
- **Safety:** Adapt message append and link validation for the nullable-project branch without bypassing server-assigned roles (`store.py:263–276`). Enforce conversation/parent/message-reference notebook identity, and verify cell and execution receipt against that same notebook; the existing `_links` project-only message check (`:230–251`) is insufficient by itself. Preserve historical missing-cell references without retargeting them; validate new references against current saved state. No receipt, execution, or runtime changes.
- **Cross-store failure:** File creation (`notebooks/store.py:186–194`) and SQLite cannot commit atomically. If SQLite ensure fails, return an error—not a usable conversation ID—and leave the durable notebook file intact; reopening retries ensure. If the response is lost after commit, lookup returns the same ID. Do not roll back by deleting a notebook or its history.

**Scope:** Backend: `application/store.py`, `models.py`, `router.py`; `notebooks/router.py` for create/open orchestration; `main.py` only if wiring requires it. Frontend: `Workspace.tsx`, `ConversationComposer.tsx`, and the existing API/projection helpers as needed: load canonical ID from server, remove New conversation/selector and both header buttons, use View → Roadmap, retain scoped drafts and explicit legacy history. Tests: `tests/test_application.py` plus notebook HTTP/lifecycle tests; `web/src/Workspace.test.tsx`, `ConversationComposer.test.tsx`, and affected browser coverage. Cover standalone/project create, reopen/restart, concurrent ensure, migration with multiple legacy threads, membership changes, cross-notebook references, SQLite failure/retry, and UI draft/pending guards.
